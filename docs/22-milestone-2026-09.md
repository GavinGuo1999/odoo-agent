## 2. 三条站得住的设计决策

回头看，有三件事值得在下一阶段继续坚持。

### 2.1 模型交的是契约，不是 SQL

模型返回的是 `{plan, sql}`：先声明"我按月分组、用了这两个过滤条件、输出这两列、
按 month 升序"，再写出与声明一致的 SQL。守卫用 AST 逐项比对。

价值不在于挡住 `DROP TABLE`——那太容易了。价值在于挡住**看起来正常但悄悄变了范围**
的查询：模型偷偷加一个 `partner_id = 5`，计划里没声明，直接拒。

本阶段一个真实收获：这套契约**会误伤**。CTE 的计算列、补充查询、自然语言点名客户，
都曾被合法地拒掉。每一次误伤的修法都是**收紧判据而不是放宽**——比如"过滤值逐字
出现在问题里"比"问题里有'客户'二字"更严格，同时又解开了正确的用法。

### 2.2 安全边界靠结构保证，不靠提示词

没有任何一条图的边能绕过 `validate_sales_sql`。补充查询这个新功能加进来时，
它复用的是**同一个** guard 实例，而不是一份"补充查询版"的检查。

执行层还有两道独立防线：连接串上的 `default_transaction_read_only=on`，
以及只读数据库角色。AST 检查被绕过了，PostgreSQL 还会拒绝。

### 2.3 确定性优先，模型只在必要处介入

意图路由是关键词而不是模型；图表类型先有确定性回退再让模型微调，且模型只能返回
受约束的 `ChartPlan`，碰不到 ECharts 配置；答案在结果简单时走确定性摘要，
省掉第二次模型调用。

代价是脆——路由认"原因"不认"为啥"。但它可测、可回归、改一个词修一个 case。

## 3. 诚实的边界

这些不是"还没做"，是**当前架构下就不打算做**或**做不到**的。

| 边界 | 说明 |
| --- | --- |
| 单公司、单用户 | 门禁只有一个口令，分不清是谁在用，也没有审计到人 |
| 9 张表 | 采购、库存、会计、制造一概答不了。覆盖面是用确定性换来的 |
| 没有退款口径 | 8 个指标全基于 `sale_order`，没有 `account_move`，退款不会从销售额里扣 |
| 只读 | 不写任何数据。这是设计而非限制 |
| 因果解释靠证据不靠推理 | "为什么下降"只能给出下钻数据，不能给出业务归因 |
| 单模型供应商是单点 | 余额耗尽会让整站不可用，没有降级路径（本阶段实际发生过一次）|

| 债务 | 利息 | 触发条件 |

## 5. 下一阶段的三个候选方向

按"投入产出"排，**建议只选一个**。

### 方向 A：把演示变成可交付（工程收口）

补 2024 年数据、启用 HTTPS、复测 A/B、做延迟优化。

- 适合：近期要真的拿给客户看
- 产出：一个能给别人用的东西，而不是一个能给别人看的东西
- 风险：低。全是已知问题的收尾

### 方向 B：扩语义层到第二个业务域（产品深度）

采购或库存。边际成本比第一个域低很多——Guard、结果签名、A/B 基准都是现成的。

- 适合：想验证这套架构能不能复制
- 前置：**必须先和业务确认口径**，否则重演"退款算不算"这类问题
- 风险：中。口径讨论比写代码慢

### 方向 C：把确定性部分也纳入可观测（质量深度）

现在 Langfuse 只看得到模型调用；路由判定、守卫拒绝了什么、契约哪一条没过，
全都不在 trace 里。执行链路面板是第一步，但它只到前端，没有沉淀成可查询的数据。

- 适合：想知道"线上到底哪类问题在失败"
- 产出：从"我修了一个 bug"变成"我知道这类 bug 占多少"
- 风险：低，但收益要积累时间才显现

---

**我的建议**：先做 A。这一阶段暴露的缺陷里，有相当一部分是在真实提问下才现形的
（CTE 同比、点名客户、Top-N 措辞）——继续加功能只会让这类问题更晚被发现。
把现有的东西做到能交付，是发现下一批真实缺陷最快的方式。
